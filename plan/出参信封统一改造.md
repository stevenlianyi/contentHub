## 1. 背景与现状

### 1.1 「平铺」的根因

所有端点出参都在 `subfunc/apiCommon.py::genRtnResult()` 收口，其关键行为是把业务载荷**平铺**到信封顶层：

```python
rtnSet = comFC.rtnMSG(errCode, rtnField, lang, msgKey)
result.update(rtnData)      # ★ 业务字段直接摊在顶层
result["CMD"] = CMD
result["msgKey"] = msgKey
result["MSG"] = rtnSet["MSG"]
result["errCode"] = errCode
```

因此**是否出现顶层 `data` 键，完全取决于各处理器 / `processor/*` 传入的 `rtnData` 里本身有没有 `data` 键**，历史上形成了三种形态并存的局面：

| 形态 | 判定 | 典型来源 |
|---|---|---|
| ① 平铺 | 顶层无 `data` 键，业务字段直接摊在信封顶层 | 事务类端点（`topicadd` / `layoutdel` / `publishcheck` / `topicrender` …） |
| ② 查询内层 | 顶层 `data` 为**数组**，另带 `total/beginNum/endNum/indexKey` | 走 `common/queryBufferCommon.getQueryBufferComplte()` 的查询类端点 |
| ③ 记录内层 | 顶层 `data` 为**业务记录副本**（非查询语义） | `assetadd` / `topicassetadd`（把整条记录塞进 `data`），以及 `topicrender` / `publishpush` 的**失败路径**（`data` 携带 `jobID/jobCode` 等诊断信息） |

形态③的存在说明「有没有 `data` 键」并不能作为判断依据 —— 这也是本次必须用**显式域清单 + 显式查询类清单**而非结构启发式的原因。

### 1.2 出口与账本字段

`main/chAPIPost.py::post()` 是 `/chapi` 的**唯一出参出口**（见 §6.1 出口唯一性证据）。改造前出口顺序为：

```
fillFileUrlsInResult(rtnData)   # fileID -> URL，只加工传入对象的一层字段
normalizeMsgKey(rtnData)        # msgKey 归一到 contenthub
rtnData["SN"], rtnData["YMDHMS"]
```

信封账本键为 `CMD / msgKey / MSG / errCode / SN / YMDHMS`。

## 3. 目标出参契约

### 3.1 account 域（copy）

```jsonc
{
  "healthSummary": { "total": 3, "OK": 2, "EXPIRING": 1, "INVALID": 0, "UNKNOWN": 0 },
  "checkedAt": "20260921120000",           // 原有顶层业务字段: 一律保持不变(字段名/类型/取值)
  "data": {                                // ★ 新增: 顶层业务字段的副本(不含信封键)
    "healthSummary": { "total": 3, "OK": 2, "EXPIRING": 1, "INVALID": 0, "UNKNOWN": 0 },
    "checkedAt": "20260921120000"
  },
  "CMD": "accounthealth", "msgKey": "contenthub",
  "MSG": { "errCode": "B0", "content": ";" }, "errCode": "B0",
  "SN": "1", "YMDHMS": "20260921120000"
}
```

- 顶层已有 `data` 时**不覆盖**（透传账号服务回包场景），避免破坏下游语义。

### 3.2 ch_* 域 · 非查询类（move）

```jsonc
{
  "data": { "recID": "7" },      // ★ 原有顶层业务字段整体迁入
  "CMD": "topicadd", "msgKey": "contenthub",
  "MSG": { "errCode": "B0", "content": ";" }, "errCode": "B0",
  "SN": "1", "YMDHMS": "20260921120000"
}
```

- 原先自带 `data` 子键的端点（`assetadd` / `topicassetadd` / `topicrender` 失败路径 / `publishpush` 失败路径）**机械迁移**为 `data` 内的子键，语义零改动。
- 无业务字段时 `data` 为 `{}`（异常兜底 `ERR_GENERAL`、占位端点 `C2`）。

### 3.3 查询类（keep，共 14 个）

```jsonc
{
  "data": [ { "…": "…" } ],      // 数组, 不变
  "total": 128, "beginNum": "0", "endNum": "20", "indexKey": "topicqry_xxx",
  "CMD": "topicqry", "msgKey": "contenthub",
  "MSG": { "errCode": "B0", "content": ";" }, "errCode": "B0",
  "SN": "1", "YMDHMS": "20260921120000"
}
```

### 3.4 信封账本键恒留顶层

`CMD / msgKey / MSG / errCode / SN / YMDHMS` **不进入 `data`**。未注册命令 / 频次限制等框架级返回（`ERR_NOCMD` / `ERR_IPFLOOD`）保持原样。

## 4. 实现

### 4.1 落点（单点收口）

在 `main/chAPIPost.py::post()` 唯一出口插入一次整形调用：

```python
fillFileUrlsInResult(rtnData)

#出参信封整形(见 plan/出参信封统一改造.md): 查询类维持原结构, 其余按域取 CMD_OWNER 分派
#(account -> 顶层保留 + data 副本; ch_* -> 业务字段整体迁入 data; 未注册 CMD -> 原样)
#★ 必须排在 fillFileUrlsInResult 之后: fillFileUrls 只加工传入对象的一层字段
if CMD not in apiCommon.QUERY_CMD_LIST:
    rtnData = apiCommon.normalizeEnvelope(rtnData, CMD_OWNER.get(CMD, ""), CMD)

normalizeMsgKey(rtnData)
rtnData["SN"] = localSN
rtnData["YMDHMS"] = misc.getTime()
```

选择出口收口的理由：

- `subfunc/crudApi.py` 是生成件（`#===== auto-generated crud sections begin/end`，由 `tools/mergeCrudApi.py` 覆盖，禁止手改）→ 出口收口可保证**重跑生成器不回退**；
- `processor/*` 与 `common/*` 的返回契约 `{"errCode","field","errMsgList","data"}` **零改动**，服务层测试不受影响；
- 单点实现、单点测试。

### 4.2 出口执行顺序（关键）

```
业务返回 rtnData
→ fillFileUrlsInResult(rtnData)     # 必须在前
→ normalizeEnvelope(…)              # 新增
→ normalizeMsgKey(rtnData)
→ rtnData["SN"]; rtnData["YMDHMS"]
```

1. `comCh.fillFileUrls` 只加工**传入对象的一层字段**。放在整形前：account 域顶层 `xxxUrl` 照旧生成（随副本一并进 `data`，不丢）；ch_* 非查询类先完成转换再整体迁入 `data`，`data` 内仍含 `xxxUrl`；查询类本就取顶层 `data`（数组）加工，行为不变。
2. 若先整形再 `fillFileUrls`，account 双写场景会出现「顶层字段已无 fileUrl」的行为回退，必须避免。
3. `SN/YMDHMS` 最后写入，确保不被卷入 `data`、也不进入 account 的副本。

### 4.3 整形函数（纯函数）

```python

ENVELOPE_KEY_SET = {"CMD", "msgKey", "MSG", "errCode", "SN", "YMDHMS"}
QUERY_CMD_LIST   = [ …14 项… ]      # 显式清单, 见 §2.3
ACCOUNT_OWNER    = "account"

def normalizeEnvelope(aResult, owner = "", cmd = ""):
    """keep / copy / move 三态整形; 异常绝不外抛(仅 warning 并返回原结果)。"""
```

实现要点：

| 要点 | 说明 |
|---|---|
| 分域依据 | `subfunc.CMD_OWNER`（导入期由 `MODULE_MAPS` 派生）的路由标签，**不含角色/表/状态/合规业务规则** —— 属 `apiCommon` 零业务约束的显式豁免项（已在文件头注释登记） |
| 为何不用启发式 | `topicversionqry` 单条快照分支的 `data` 是**对象**，用「data 是否数组 / 是否含 indexKey」判定会误判并二次嵌套 → 必须用显式 `QUERY_CMD_LIST` |
| 幂等保护 | `move`：非信封键仅剩 `data` 时判为已整形，直接返回；`copy`：顶层已有 `data` 时跳过 |
| 不破坏入参 | `move` 构造新字典返回，不删除 `processor` 返回字典的键；`copy` 原地补键 |
| 异常隔离 | 内部 `try/except` 全包，失败仅记一条 warning（含 PID/CMD），返回原结果 —— 「整形失败不改变可用性」 |
| 日志 | 正常路径**不打日志**（避免 72 端点刷屏） |
